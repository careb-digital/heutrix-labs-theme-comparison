# Service changes moved with one owner and one next action

> **Anonymised founder-delivery experience.** This case draws on operational workflow improvements delivered by Heutrix founders while helping run care-provider services. Identifying details are withheld. It is not presented as a Heutrix client engagement.

## The operational stakes

Requests affecting an existing service moved through operations, rostering, administration and management. Staff communicated actively, but the status still lived inside the latest message.

A request described as “with rostering” might actually be waiting for a management decision. A manager could approve a change without every downstream team seeing the same instruction. The person coordinating the request became the human integration between systems.

| Starting point | Delivered operating change | Observable result |
|---|---|---|
| Requests and decisions buried in handover messages | One request state with owner, decision, dependency and completion check | Teams could distinguish what was requested, what was approved and what action remained |

## The real constraint

The workflow did not separate a requested change from an authorised change. One status attempted to summarise several different actions, and a completed task did not prove that every required handover had occurred.

## What changed

The founders mapped the path from a general request to an authorised decision and operational completion.

- A structured request captured the minimum coordination information.
- The current owner and next action remained visible.
- “Information needed” was separated from “awaiting decision”.
- The authorised decision was recorded without being rewritten by downstream teams.
- Operational actions were assigned only after approval.
- Closure required the agreed handovers to be confirmed.

Funding, service, staffing, clinical, contractual and risk decisions stayed with the organisation’s authorised roles.

## The operating result

Teams stopped using the latest email as the source of truth. Each function could see when the work genuinely reached it and what it was expected to do. Managers could focus on decisions and blockers instead of translating status between teams.

## Proof boundary

This case supports a qualitative claim about operational ownership and handover. It does not claim a response-time reduction, service outcome or integration. Those would require the original baseline, scope and permission.

## How Heutrix would scope it today

This pattern maps to **Heutrix Workflow Transformation** for one bounded service-change coordination flow. Acceptance would test an approved request, declined request, missing information, changed priority and several downstream tasks.

Bring one change-request type and the point where ownership becomes unclear to a 20-minute, no-obligation workflow fit call. Keep the description general and non-sensitive.
